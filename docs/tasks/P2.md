# P2 brief: training and evaluation

> For P2 and for P2's AI assistant. Read this file, then `rules.md` and `idea.md`.
> Repo: https://github.com/incompetant-jellyfish/Optima-luna · Deadline: **submit by 6:45 AM, 22 Nov** (hard deadline 7:00).

## Your role

You own **every training run** and every result that comes out of one: model metrics, predictions, landing–ice pairs and validation against known sites. Nobody else trains.

- **P1** makes the data: `features.parquet` plus the single scoring definition.
- **P3** presents it: the dashboard, README, deck and video.
- You sit in between: **features in → results out.**

> AI assistant? Read `docs/tasks/P2_GUIDE.md` first (current state + exact tasks).

> Note: `model.py` uses scikit-learn's `MLPRegressor`, which runs on the **CPU** only. Your GPU isn't used and isn't needed: about 290k cells × 12 features trains in minutes. Don't port it to PyTorch tonight.

## Steps

### 1. Unpack the overlay into real commits (do this first, ~20 min)

On a branch `p2-model`:

1. Copy `src/synth.py`, `src/model.py`, `src/pairing.py`, `src/explain.py`, `src/validate.py`, `tests/test_*.py` and `docs/VALIDATION.md` into the repo.
2. **Do not replace `README.md`, `AI_USAGE.md` or `ACKNOWLEDGEMENTS.md`.** Other people's entries are already in them. Merge your sections in by hand.
3. Append `config.validation.append.yaml` to the **end** of `config.yaml`. Don't touch the rest of the file.
4. Remove both upload copies once the files are in place: `git rm -r optima-luna-p2-overlay.zip optima-luna-p2-overlay/`. Judges must see the code in `src/` and `tests/`, not a zip or a nested copy. While those copies sit there, `pytest` doesn't run their tests.
5. Add `joblib` to `requirements.txt`, pinned to the installed version (`.venv/bin/pip freeze | grep joblib`).
6. Add these Makefile targets (copy the style of the existing ones):
   ```make
   synth:    $(PY) -m src.synth
   model:    $(PY) -m src.model
   pairs:    $(PY) -m src.pairing
   validate: $(PY) -m src.validate
   ```
7. `make test`: everything green, including P1's grid tests and P3's app test.
8. Commit with a clear message, then merge to `main`.

**Done when:** no zip in the repo, `make test` passes, and `make synth model pairs validate` runs end to end.

### 2. Write results to `results/` (committed to git)

`data/` and `models/` are git-ignored, so the demo laptop and judges never see them. Change the outputs so a **slim copy** lands in a new `results/` folder that *is* committed:

| File | Columns / content |
|---|---|
| `results/predictions.parquet` | `cell_id, landing_score, resource_score, landing_uncertainty, resource_uncertainty, confidence` (float32), plus a `features_version` column |
| `results/pairs.parquet` | Output of `pairing.py`: `landing_cell_id, ice_cell_id, distance_km, route_cost, landing_score, resource_score, confidence, combined_score` |
| `results/metrics.json` | Existing `metrics.json`, plus `"features_version"` and the training time in seconds |
| `results/validation.csv` | Output of `validate.py` |

Rules:
- Keep each file under about 20 MB. Leave out the raw feature columns; P3 joins on `cell_id`.
- Scores are **0–1**. P3 multiplies by 100 for display.
- `features_version` is one of `v0-synthetic`, `v1-lola`, `v2-lola-diviner`. Every result file must say which one it came from, because results from synthetic data must never be presented as real.

### 3. First training run on synthetic data (v0)

- Run `make synth && make model && make pairs && make validate`, and **time the model step**.
- Read `metrics.json`. Is the MLP ≥ the Ridge baseline when inputs are masked? Write the answer down honestly either way.
- Commit `results/` as v0 and tell P3 the files exist.

This run is to shake out bugs before real data arrives. Don't tune hyperparameters on synthetic data.

### 4. Switch to P1's scoring (when P1 says `scoring.py` is on main)

`model.py` has its own `_weighted_score`. Replace it with P1's API, so there is **one** scoring definition in the repo:

```python
from src.scoring import score      # P1
scored = score(features)           # returns landing_score, resource_score,
                                   # landing_confidence, resource_confidence, confidence, eligible
```

The pseudo-labels then come from `scored`. Re-run step 3 and check the tests still pass.

### 5. Retrain on real data (when P1 sends `features_v1.parquet`, then v2)

1. Put the file at `data/processed/features.parquet`. P1 sends it via the shared Drive folder or USB.
2. `make model pairs validate`, then commit `results/` with the new `features_version`.
3. **Send P3:**
   - R² on held-out blocks for landing and resource, MLP vs baseline, masked and unmasked
   - training time
   - for Shackleton rim and Malapert massif: in the top-K or not, and their ranks

   These go straight onto deck slide 4.

### 6. `docs/VALIDATION.md`

Write up the real outcome:
- which features version was used
- top-K
- each reference site's rank
- **any misses, and which feature pulled the site down** (use `explain.py`)

Failures are reported, never hidden (rules §3).

## Rules that apply to you

- **Never fabricate or round up results** (rules §3). If the MLP loses to the baseline, say so.
- `ACKNOWLEDGEMENTS.md`: add every new library (joblib, and so on) when you add it.
- `AI_USAGE.md`: add a row for every significant AI-generated module.
- Every module needs a short docstring explaining what it does and why. You'll be asked about it.
- Small commits with clear messages. Never commit `.env` or data files other than `results/`.
- Be ready to answer these at judging:
  - Why pseudo-labels?
  - Why spatial blocks rather than random cells?
  - What does masking buy you?
  - What do the uncertainty numbers mean?
